## 2. 维度一：实时与安全时序（8 条）

### 1.1 保护停波路径分级与单所有者

- **档位：明确收益**（过流部分澄清与锁存化）；其中端口停波硬件联动为**需权衡**。
- **现状证据**
  - firmware-architecture.md:10：「过流检出、过流锁存、端口停止等保护事件→脉冲引擎任务队列，容量 4，不可丢弃、溢出时合并为多源事件并计数（停波本身由 ISR 快速路径直接完成）」；
  - firmware-architecture.md:44「硬件路径执行即时封锁，中断捕捉故障来源及边界」；:70「过流锁存保护沿硬件通路执行，端口快速停波由板级中断直接执行」；
  - mcu-pinmap.md:133-139：FLT4/FLT5 ← COMP，**复位模式=条件复位、滤波=无**，故障输出电平 INACTIVE；
  - mcu-pinmap.md:229「过流锁存停波独立于 NVIC 调度」；
  - SRS E-001（pulse-gen-firmware.md:179）、T-005（:155）、F-012（:40）、PRM-509/510（params.md:157-158）、N-004（:197）。
- **问题本质**
  1. 过流停波事实上有两套并存的实现面：COMP→FLT 硬件通路（自动把 TA1/TA2 打入故障态）与"ISR 快速路径"，但文档未明确 ISR 在过流路径上**是否需要写任何输出寄存器**——若 ISR 再写一次封锁，与硬件通路形成重复与竞态；若不需要，则"ISR 内直接完成停波"的表述有误导。
  2. 更尖锐：**条件复位 + 无滤波**意味着过流检出（COMP 电平）消失后 HRTIM 自动恢复输出；而业务语义是"过流终止后保持停波状态，直到 0x3D 清除"（pulse-engine.md:9、E-005）。在"硬件自动恢复"与"ISR/任务软件封锁"之间若存在任何窗口，故障后可能重放一次脉冲——这是安全路径上不应存在的设计缝隙。
  3. 端口停止（PB4 负向沿）只有软件 ISR 一条路，其最坏延迟上界在 SRS F-012 中注明"待 PSG-03 专项"，架构层没有给出可核算的路径定义。
- **优化提案**
  1. 按触发类别钉死**停波单所有者矩阵**：过流检出与过流锁存 → 停波唯一由 HRTIM 硬件故障态完成（故障输出电平 INACTIVE），ISR 只捕捉故障来源与 ADC 样本边界，**不写输出寄存器**；端口停止 → ISR 快速路径写输出封锁（两条寄存器写），随后入队事件。把这条矩阵写进 sequence_io.h/psg_protection.c 的接口约定。
  2. 过流检出的故障复位模式从「条件复位」改为「锁存（latch）」或条件复位 + ISR 内立即封锁并保持（软件封锁直到运行控制解除），消除故障消失后的自动重放窗口；复核 PRM-716（FLT 计数 2）与锁存化的交互。
  3. 端口停止评估硬件联动：若 RM0440 支持把 EXTI4/片上事件接入 HRTIM EEVx 或 SWFLT，把软件停波升级为硬件事件停波；若不可行，明确接受 ISR 方案并给出"ISR 写封锁 + 事件入队"的 WCET 与最坏延迟预算（与本图 1.4 联动）。
- **取舍与代价**：锁存化改变 mcu-pinmap.md:137 的固定配置并需要台架重验 T-005；端口硬件联动依赖 RM0440 EEV 源核查，可能不可行。
- **影响条款**：E-001、E-005、E-010、F-012、F-042、T-005、PRM-509/510/716、N-004、mcu-pinmap.md §2.4.3、firmware-architecture.md:10/44/70。

### 1.2 ADC 采样窗 257 ns > 最短脉宽 200 ns 的回退阶梯

- **档位：需权衡**（涉及 PRM-710/PRM-705 固定值修改与 T-007 全范围复测）。
- **现状证据**
  - firmware-architecture.md:45：「ADC 采样阶段约 257 ns（PRM-708、PRM-710）长于最短目标脉宽 200 ns（PRM-307、PRM-308），采样窗口有效性与台架验证回退方案见串级结算设计」；
  - current-settlement.md:16：257 ns vs 200 ns，IGBT 导通约 34 ns / 关断约 282 ns，差值约 248 ns 使功率输出脉宽相对驱动脉宽延长；
  - params.md:184-186：PRM-708 = 48.57 MHz（VCO 340 ÷ P=7）、PRM-710 = 12.5 周期（12.5/48.57 ≈ 257 ns）；params.md:107-108：PRM-307/308 = 0 或 200–5000 ns；
  - mcu-pinmap.md:70、:145-146：采样时间与 TRG1/TRG3（Timer B CMP3/CMP4）触发；
  - SRS F-035（:81）「每个非零脉冲持续时间窗口采 1 个点」、T-007（:157）电流精度、T-006（:156）外推精度、F-024/F-025（:57-58）。
- **问题本质**：采样窗物理上宽于最短目标脉宽，单样本可能跨沿；当前文档只承诺"台架验证"，未把回退方案固化为可执行的设计阶梯——一旦台架不达标，设计变更的评估依据悬空。
- **优化提案（三级回退阶梯，逐级激活）**
  1. **零改动**：触发相位锚定——TRG1/TRG3 由 Timer B CMP3/CMP4 产生，把采样窗中心对准"拉长后的功率平台"（驱动沿 +34/-282 ns 差 ≈ +248 ns 平台加宽）。台架确认 257 ns 窗可整体落入平台后即锁定此方案；
  2. **改 PRM-710**：采样时间 12.5 → 6.5 周期，窗宽 134 ns < 200 ns。代价：12 位精度下的采样裕量下降，需核对前端源阻抗并全范围复测 T-007（±2%读数+0.2 A）；
  3. **改 PRM-705**：PLL P 7 → 6，ADC 时钟 48.57 → 56.67 MHz（≤ STM32G4 的 60 MHz 上限，且 PLLP 只供 ADC 支路，SYSCLK/HRTIM/USART 不受影响），6.5 周期 = 115 ns（12.5 周期 = 220 ns 仍不达标，须与第 2 级组合）。
- **取舍与代价**：第 1 级零成本但依赖台架结论；第 2/3 级改动固定 PRM 并连带复测 T-007/T-001。
- **影响条款**：PRM-705/708/710、F-035、T-001、T-006、T-007、mcu-pinmap.md §2.1/§2.4.4、current-settlement.md:16。

### 1.3 串级结算截止路径：跨任务跳数压缩与唤醒语义钉死

- **档位：明确收益**（语义澄清部分）；任务合并取舍为**需权衡**。
- **现状证据**
  - firmware-architecture.md:10：「串结束（HRTIM TIMA）→脉冲引擎任务队列，容量 2，队列满视为失约并按 F-041 终止运行；DMA 半传输/传输完成就绪→结算任务队列，容量 2」；
  - current-settlement.md:9：「串结束与各通道的就绪事件经队列交**结算任务**。收齐同一串的出波结束事件和各参与通道的就绪事件后，结算任务优先遍历该串的有效样本」；
  - firmware-architecture.md:25：「根据结算依据与截止时间决定是否发出下一串许可」（运行控制/脉冲引擎任务）；
  - current-settlement.md:18：「从最后一个实际电流采样窗口到 DMA 就绪、结算任务取数、双路判定和下一串许可，测量并分段记录耗时……核对最短 1 ms 串间隔的余量」；
  - params.md:74-76：PRM-117 结算任务唤醒周期 10 ms（可配宏）、PRM-118 <50 ms、PRM-119 ≤40 ms；params.md:106：PRM-305 脉冲串间隔 100–10000×10 µs（最短 1 ms）；
  - SRS F-038（:84）、F-040（:86）、F-041（:87）。
- **问题本质**
  1. **事件流向矛盾**：串结束事件按 firmware-architecture.md:10 进脉冲引擎队列，但结算任务需要收齐它才能结算——跨任务转发路径未定义，1 ms 截止路径上多出一跳或一段未描述的逻辑。
  2. **唤醒语义风险**：PRM-117 = 10 ms 周期 > 最短串间隔 1 ms。若结算任务按 10 ms 周期轮询，串级截止（F-041：下一串原定开始时刻）在设计上违约；结算任务必须**事件驱动**（队列阻塞唤醒），PRM-117 只能作为群级结算的等待周期。
- **优化提案（方案 A 推荐）**
  - 事件流改为单队列收齐：TIMA ISR 将串结束事件**直接入结算任务队列**（脉冲引擎任务如需串推进事实，由结算任务判定完成后用 FreeRTOS TaskNotification 通知，或 ISR 同时投递轻量标志）；结算任务 `xQueueReceive(portMAX_DELAY)` 事件驱动；判定完成后经任务通知直接唤醒脉冲引擎任务执行"放行下一串 / F-041 终止"。
  - 文档明确：**PRM-117 仅约束群级结算等待**，串级结算为事件驱动、无周期延迟。
  - 方案 B（合并）：脉冲引擎与结算合并为单一高优先级任务，事件单队列零跨任务跳；代价是任务 WCET 合并，PRM-117~119 预算与出波推进、0x30 受理互抢，上界更难证。
- **取舍与代价**：方案 A 增加一个任务通知点但保住 PRM 预算分离；需给出 1 ms 串间隔下的逐段预算表（ISR 延迟 + 入队 + 任务切换 + 结算 WCET + 通知 + 许可写寄存器）作为 F-041 验收基线。
- **影响条款**：F-038、F-040、F-041、PRM-117~119、PRM-305、firmware-architecture.md:9-10 任务清单与交接契约表、current-settlement.md:9。

### 1.4 ISR 最坏延迟预算与 FreeRTOS 中断阈值钉死

- **档位：明确收益**。
- **现状证据**
  - firmware-architecture.md:11：「FreeRTOS 管理的 ISR 只使用 FromISR 接口入队或发通知」；:12「中断抢占延迟计入 T-007、T-008 验收」；
  - params.md:202-206：PRM-726 分组 = 4 位抢占；保护类（EXTI4/EXTI9_5/HRTIM1_FLT/HRTIM1_TIMA）优先级 4，DMA/USART 优先级 5，SysTick 15；
  - mcu-pinmap.md:229：「同级中断彼此不抢占，同时挂起时按 IRQ 编号处理」；
  - SRS F-012（:40）端口停波最坏延迟上限"待 PSG-03 专项"、T-005（:155）、T-007（:157）、N-004（:197）。
- **问题本质**
  1. **FreeRTOS 中断阈值未钉死**：全仓库无 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 表述。FreeRTOS 默认值为 5，意味着优先级数值 4 的保护类 ISR（含需要入队串结束/保护事件的 HRTIM1_TIMA、EXTI4/9_5）**不得调用 FromISR API**，与 firmware-architecture.md:11 的约定直接冲突；必须显式设为 4（或更低数值）并写入板级配置与验收。
  2. **无 ISR WCET 预算数值**：EXTI9_5 同时覆盖 PB6/PG7/PG8 三源判定；同级不抢占意味着端口停波（EXTI4）的最坏延迟 = 同级最长 ISR WCET + 中断压栈，没有数值就无法兑现 F-012 的停波延迟上界。
- **优化提案**
  - 钉死 `configMAX_SYSCALL_INTERRUPT_PRIORITY = 4`（4 位抢占分组下），登记进 PRM-7xx 或板级配置，注明 0-3 段预留不用；
  - 为每个保护类 ISR 定义 WCET 预算（建议 <2 µs @170 MHz ≈ 340 周期）：EXTI4 = 读边沿 + 2 条封锁写 + 入队 + 清标志；HRTIM1_TIMA = 读状态 + NDTR 快照（见 1.8）+ 入队 + 清标志；EXTI9_5 = 三源位测试 + 同上；
  - 给出端口停波最坏延迟公式：`压栈 + 同级最长 ISR WCET + EXTI4 WCET`，供 F-012/T-005 验收引用。
- **取舍与代价**：阈值改为 4 使 FreeRTOS 关键区对优先级 4 ISR 可见（正常做法，内核关中断区间本应极短）；需在 psg_board_config.h 与 FreeRTOSConfig.h 双侧登记。
- **影响条款**：F-012、T-005、T-007、T-008、N-004、PRM-726~730、firmware-architecture.md:11-12、mcu-pinmap.md §2.8。

### 1.5 0x30 受理自检 5 ms 等待：快速路径与挂起式等待

- **档位：明确收益**。
- **现状证据**
  - params.md:160-161：PRM-512 锁存清除确认等待 = 5 ms（重复登记两行，本身待清理）；
  - SRS E-003（pulse-gen-firmware.md:181）：「读取两路锁存输入电平，**任一路有效**即执行过流锁存复位，等待锁存清除确认等待（PRM-512）后重读，仍有效则置 bit0」；上电自检、0x30 受理、触发间歇均执行；
  - SRS E-002（:180）：「空闲时任一通道过流锁存由无效变有效……主动上报 0x11」——空闲期锁存电平已被 EXTI9_5 持续监控；
  - pulse-engine.md:5、firmware-architecture.md:26（0x3D 的复位脉冲 → 5 ms → 重读在同一业务裁定内）；params.md:60：PRM-103 动作类响应时限 ≤50 ms。
- **问题本质**：0x30 受理路径上，当锁存有效时存在 5 ms 同步等待。若实现为忙等，脉冲引擎任务 5 ms 不能处理任何保护/推进事件（FreeRTOS 下可用挂起式延迟，但文档未约定实现方式）；且"先读电平、无效即免等待"的快速路径未显式化。
- **优化提案**
  1. 把 E-003 的流程显式化为两分支：**锁存无效 → 立即受理**（快速路径，占比绝大多数，0x30 应答回到毫秒级）；**锁存有效 → 复位脉冲 + 挂起式等待**（FreeRTOS `vTaskDelay` 或时基到期唤醒，禁止忙等），5 ms 计入 PRM-103 的 50 ms 预算（最坏 5 ms + 重读 + 载荷处理远小于 50 ms，可核算）；
  2. 空闲期锁存监控已由 EXTI9_5 完成（E-002），据此把"0x30 受理时的锁存状态"定义为以最近一次锁存事件为准的单一事实源，消除任务内再读的电平竞态；
  3. 0x3D 的 5 ms 等待同样改为挂起式，并把 PRM-512 的重复登记行合并。
- **取舍与代价**：无功能牺牲；需要明确"5 ms 等待期间收到新 0x30/0x3D 请求"的排队语义（状态矩阵已裁决，串行化即可）。
- **影响条款**：E-002、E-003、I-011、I-021、PRM-103/512、firmware-architecture.md:26、pulse-engine.md:5。

  - SRS E-008（:186）：「验收时使任一关键模块持续阻塞，同时保持其他模块可调度，验证看门狗触发复位」。
- **问题本质**：监视周期、拒喂阈值（逾期次数）、最坏喂狗间隔三者无数值；且任务监视器与受监视任务之间若共享任何互斥量，可能被阻塞在低优先级任务上，既威胁检测正确性（漏检）又威胁喂狗及时性（误复位）。
- **优化提案**
  1. **零共享资源**：任务监视器只读各任务的原子推进标记（单调计数/时基戳），不持任何互斥量，喂狗路径 WCET 静态可证；推进标记由各任务在关键推进点自增，空闲健康态也周期性推进（满足 E-008"正常等待且无逾期工作时健康检查应通过"）；
  2. **数值化**：监视周期建议 100 ms；每任务逾期判定用其最大推进间隔（firmware-architecture.md:53-59 已核定依据，补具体数值）；拒喂阈值 = 连续 2 次逾期采样；由此推导最坏拒喂延迟 ≤ 3×监视周期 + 判定余量 ≪ 0.941 s，最坏喂狗间隔 = 监视周期 + 监视器自身被 ISR 抢占上界（用 1.4 的 ISR WCET 预算核算）；
  3. 标识服务推进间隔（页擦除 24.47 ms）与监视周期（100 ms）对比：24.47 ms < 100 ms，单步擦写不会误判逾期，写入核验公式。
- **取舍与代价**：无功能牺牲；需要把"拒喂阈值"从板级配置上浮为受控参数并登记。
- **影响条款**：E-008、PRM-603/718-720/739、firmware-architecture.md:51-62、ADR 0001。

### 1.7 HRTIM 串边界机制：REP 硬件定界 vs 软件计数（突发模式用途随之落地）

- **档位：需权衡**（涉及 PRM-715 固定值修改与 §2.4.1 配置改动）。
- **现状证据**
  - params.md:192：PRM-715 HRTIM 重复计数 = 0（固定）；mcu-pinmap.md:114：重复计数「更新禁用」；
  - mcu-pinmap.md:156：突发模式触发源 =「Timer A 重复」；:150-155：单次（SINGLESHOT）、时钟 fHRTIM ÷ PRM-717（÷512 ≈ 332 kHz，params.md:193）；
  - mcu-pinmap.md:163：TIMA 重复（REP）→ `HRTIM1_TIMA_IRQn`；firmware-architecture.md:10 将「串结束（HRTIM TIMA）」作为串结束事件源；
  - params.md:104：PRM-304 波形数 1–256（每串波形单元数）；SRS F-023（:56）群内串重复同一波形、T-001~T-004（:151-154）。
- **问题本质**：每串波形数 N（1~256）没有硬件定界机制：REP=0 且更新禁用时，"重复事件"每个波形单元周期都产生——若按 firmware-architecture.md:10 用 TIMA 作串结束，ISR 最坏 256 次/串（300 串/群 → 7.68 万次中断/群）；若软件计数 N 个周期判串结束，串结束时刻带 ISR 调度抖动且 CPU 负担更重。突发模式的"Timer A 重复"触发源含义随 REP 语义悬空。
- **优化提案（方案 A 推荐）**
  - REP 寄存器按每串 `N-1` 装载（重复计数"更新禁用"改为**更新使能**，串间窗口由任务写 REPR），TIMA REP 中断 1 次/串 = 硬件精确串结束，零抖动；PRM-715 从"固定 0"改为"按 PRM-304 派生"；
  - 突发模式单次（SINGLESHOT）以 REP 事件为触发，在**群边界**把下一群的 CMP 参数突发重载（群内串重复同一波形，跨群才换参数），使群切换无软件抖动；这与 §2.4.1"预装载禁用"需一并复核（突发模式写预装载寄存器与"预装载禁用"的组合待 RM0440 核对）。
  - 方案 B：维持 REP=0，软件计数 + TIMA 更新中断逐周期判定；代价如上（ISR 风暴 + 抖动），仅当 REP/预装载方案被 RM0440 细节否决时采用。
- **取舍与代价**：改动固定 PRM 与 §2.4.1/§2.4.5 两处配置，需台架验证 T-001~T-004 与 F-023；需核对 RM0440 REPR/预装载/突发交互。
- **影响条款**：PRM-715、F-023、F-038、F-041、T-001~T-004、T-008、mcu-pinmap.md §2.4.1/§2.4.5/§2.4.6、firmware-architecture.md:10。

### 1.8 DMA 半区归属：从"半区=串"硬绑定改为固定缓冲 + NDTR 锚定

- **档位：需权衡**（采样归属方法学二选一）。
- **现状证据**
  - current-settlement.md:7：每路 2N×2B 循环 DMA，前后半区各容纳一串，两路合计最大 2 KiB；
  - current-settlement.md:8：HT/TC 交替发布半区就绪；跨群改样本数/参与通道时「先封锁采样触发并确认搬运已结束，再同步参与通道的 DMA 位置和串号并清除旧事件」；
  - current-settlement.md:20：勘误 ES0430 预转换样本排除在有效半区之外 → 首串物理样本数 N+1，破坏半区=串对齐；
  - current-settlement.md:11：强制中止后「部分半区的边界需由板级采集路径捕捉……DMA 剩余计数无法单独确定该边界」；
  - firmware-architecture.md:10：DMA 就绪→结算任务队列容量 2，「同一半区重复事件合并并计数」——合并键未定义。
- **问题本质**：半区=串的硬绑定在三种情形破裂（群边界变 N、勘误 N+1、中止部分半区），维护成本全压在复杂的 DMA 重同步协议上，而该协议的竞态窗口（封锁触发 vs 在途搬运）未闭合。
- **优化提案（方案 A 推荐）**
  - DMA 缓冲**固定为最大尺寸**（每路 2×256×2 B = 1 KiB，两路 2 KiB，与现状最大一致，RAM 不变），**永久不修改 DMA 长度**，只做触发启用/停止——"改长度 + 位置同步 + 清旧事件"协议整体删除；
  - HT/TC 退化为"数据就绪提示"（可合并、可丢弃，安全降级）；串边界以 **TIMA 串结束事件为锚 + ISR 内 NDTR 快照**推导：样本归属 = (串号, NDTR 区间)，跨群变 N、勘误 N+1、中止部分半区三种情形统一由同一公式覆盖；
  - 方案 B：维持半区=串，但把重同步协议规格化（合并键 = 通道×半区序号×串号，迟到事件计数丢弃）。
- **取舍与代价**：方案 A 要求 TIMA ISR 内读 2 个 DMA 通道的 NDTR（纳秒级，计入 1.4 的 ISR WCET 预算）；失去 HT/TC 的"半串提前唤醒"收益（串末才结算，无实际损失）；需台架验证 NDTR 快照与最后转换完成的同拍竞态。方案 B 保留现状语义但复杂度不降。
- **影响条款**：F-037、F-041、F-043、current-settlement.md:7-8/11/20、firmware-architecture.md:10、mcu-pinmap.md:74、SRS 勘误段落。

### 2.2 双槽快照：覆盖语义与内容精简

### 2.3 去重 FIFO：条目压缩与出队策略

- **档位：明确收益**。
- **现状证据**：params.md:49 PRM-028 深度 8 笔；params.md:27 PRM-027 事务序号 1 B、0-255 回绕；params.md:50 PRM-029 重发上限 3 次；SRS I-007（:113）原应答回放与 FIFO 边界、I-012（:123）重复握手清空去重缓存；firmware-architecture.md:17。
- **问题本质**：条目结构未定义——若按"整帧应答"存储，8×450 B（PRM-011 最大帧）= 3.6 KB 的隐性 RAM 开销；回绕窗口（序号 255→0）的旧条目误判未处理。
- **优化提案**：条目 = (序号 1 B, 命令码 1 B, 应答码 1 B, 关键短载荷引用 ≤16 B)，8 笔 ≤ 128 B；动作类命令应答均为短帧，回放时重新组帧（去重只覆盖动作类，ECSP §4.3 语义）；出队策略 = 应答发送完成后出队 + 回绕时按"序号距离窗口"判定（8 深度 ≪ 256 序号空间，无歧义）；FIFO 满时按最旧条目替换并计溢出日志。
- **取舍与代价**：回放重组的逻辑量极小；若未来动作类应答变长需复核条目上限。
- **影响条款**：I-007、I-012、PRM-027~029、firmware-architecture.md:17。

### 2.4 UART 缓冲容量数值化 + 发送队列应答预留机制化（E2 延续）

- **档位：明确收益**。
- **现状证据**：uart-reception.md:17「接收队列容量按 T-011 最坏负载核定，溢出时丢弃最旧字节并计接收溢出、触发重新同步（HW-03）」；uart-reception.md:29「应答和主动上报放入同一发送队列……为应答预留入队容量」；params.md:22 PRM-002 115200 bps（≈ 87 µs/字节）、:31 PRM-011 最大帧 450 B、:73 PRM-115 半包超时 50 ms；SRS T-011（:161）、I-008（:114）；mcu-pinmap.md:212 优先验证循环 DMA 接收。
- **问题本质**：容量仍无数值（第一轮 E4 遗留）；"预留容量"保证容量不保证时延——上报突发排在应答前仍可能拖慢应答至 T-011 边界。
- **优化提案**
  1. 接收侧：优先落地**循环 DMA 双半区零拷贝环形缓冲**（uart-reception.md:19 已有此意），容量下限 = 2×PRM-011（900 B）+ 重同步余量 ≈ 1 KiB/路；写入容量推导式（到达率 11.5 KB/s × 最坏服务间隔）与 T-011 验收联立；
  2. 发送侧：把"预留容量"升级为**应答优先级通道**——应答与上报仍共 FIFO 但应答头插（或分两个队列、发送泵按应答优先），上报仅在应答预算有余时放行；心跳（PRM-111）与 0x3C 上报的预算计入核算；
  3. 半包计时在溢出场景的行为写死：溢出 → 丢弃最旧字节 → 计接收溢出 → 重同步（HW-03），候选帧头时间戳不受溢出影响（时间戳随字节携带，见 3.3）。
- **取舍与代价**：零拷贝环形缓冲要求接收端在 HT/TC 间消费，450 B 帧 ≪ 半区容量，成立；应答头插改变发送顺序语义需在 ECSP 测试覆盖。
- **影响条款**：T-011、I-008、N-003、PRM-011/115、uart-reception.md:17/29、firmware-architecture.md:10。

### 2.5 Bank2 记录布局显式化与磨损策略裁定

- **档位：明确收益**（布局显式化）；页轮换磨损均衡为**需权衡**。
- **现状证据**：mcu-pinmap.md:25-27 双 Bank 每 Bank 256 KB、页 2 KB、PRM-739 页擦除上限 24.47 ms；params.md:168 PRM-601 Flash 上限 256 KB、:207 PRM-731 器件 512 KB；ADR 0002:1 A/B 双槽 + 槽序号 + CRC；firmware-architecture.md:34 记录范围（软件版本=编译期宏、硬件版本、序列号、标定表随固件发布）；SRS E-009（:187）、I-024（:135）。

- **取舍与代价**：裁定不均衡 = 零改动；页轮换环 = 体检逻辑复杂度上升，仅按需启用。
- **影响条款**：E-009、I-024、PRM-601/739、ADR 0002、firmware-architecture.md:34、mcu-pinmap.md §0.1。

### 3.1 任务×层职责矩阵与任务合并取舍

- **档位：需权衡**。
- **现状证据**：firmware-architecture.md:5（五层 vs 六任务交叉）、:9（任务清单）、:16-17（调度任务推进 ECSP 分派与非易失编排）；pulse-engine.md:5（ECSP 任务公共检查与去重、调度任务映射、脉冲引擎任务裁定）；current-settlement.md:9（结算任务收齐结算）；params.md:58-63（PRM-101~106）。
- **问题本质**：层与任务不是一一映射：一次 0x30 请求路径 = UART 任务(收) → ECSP(解帧/去重) → 调度任务(映射) → 脉冲引擎任务(裁定+计划) → 响应逆向 3-4 跳，每跳一次队列拷贝+上下文切换；"调度任务"承载的职责横跨 ECSP 分派与非易失编排，没有一张钉死职责的矩阵图。
- **优化提案**：产出「任务×层职责矩阵」（每任务：所属层职责、事件入口、事件出口、持有状态），并评估两个合并项：(a) 调度任务与 ECSP 分派合并为单一中优先级协议任务（请求路径减 1-2 跳，应答时限预算集中核算；代价是计划生成若误入该任务会拖长 ECSP 服务，需保持计划生成留在脉冲引擎任务）；(b) 脉冲引擎与结算合并（见 1.3 方案 B，代价大、不建议）。
- **取舍与代价**：合并 (a) 改变 firmware-architecture.md:9 的任务清单，需重算 PRM-101~106 预算；不合并则需在矩阵中写死转发契约。
- **影响条款**：PRM-101~106、T-011、F-041、firmware-architecture.md:5/9/16-17、pulse-engine.md:5、ADR 0001。

### 3.2 事件契约可测化：时间戳字段与溢出计数可查

- **档位：明确收益**。
- **现状证据**：firmware-architecture.md:10 已定义每类事件去向/容量/超限处置（第一轮 B1 已大部落地）；pulse-engine.md:7「脉冲引擎任务根据捕捉到的事件更新运行状态」；firmware-architecture.md:24「按事件发生时的运行归属区分运行中的过流与空闲过流锁存」；SRS F-041（:87 日志定位失约阶段）、E-001（:179）、N-005（:198 日志）。
- **问题本质**：事件结构体字段未规格化——"按事件发生时的运行归属"若依赖任务侧运行状态快照，运行结束瞬间的归属存在竞态（第一轮 D4 残余）；溢出计数/合并计数没有查询出口，F-041 的日志定位（"失约发生在数据就绪还是判定阶段"）缺乏可编程观察点。
- **优化提案**：sequence_io.h 层把事件契约固化为结构体：每事件携带 (类型, 运行序号, 群号, 串号, 单调时间戳, 有效样本边界)，归属裁定以事件携带的硬件事实（串号+时间戳）为准而非任务侧快照；每类队列的溢出/合并计数器纳入 0x31 或调试日志可查（发布版经 RTT ERROR 级）。
- **取舍与代价**：时间戳 4 B × 事件容量（4-8）= 32 B RAM，可忽略。
- **影响条款**：F-041、E-001、E-002、N-005、firmware-architecture.md:10/24、pulse-engine.md:7、sequence_io.h。

### 3.3 主机测试：时间注入模型与测试替身收敛（F2 延续）

- **档位：明确收益**。
- **现状证据**：firmware-architecture.md:161「主机自动化测试通过公开接口注入板级事件和带接收时刻的串口数据」、:152「主机测试可替换设备实现」；uart-reception.md:25「协议测试注入可控的字节接收时间戳」；current-settlement.md:21「人为延迟末批样本或结算任务时，核对下一串未启动……」（延迟验证无实现机制）；firmware-architecture.md:151 任务监视器直用 timebase/watchdog；SRS T-011（:161）、N-003（:196）。
- **问题本质**：主机测试能注入事件与字节，但"人为延迟结算任务""逾期/失约注入""半包计时推进"没有明确注入点；业务层若混用 FreeRTOS tick 与 timebase 时基，主机脚本时钟无法推进。
- **优化提案**
  1. 钉死双时基纪律：业务层全部经 `timebase.h` 单调时基（32/64 位定宽 + 回绕安全比较助手，第一轮 A7 残余）；FreeRTOS tick 仅用于任务延时；timebase 提供测试注入接口（set_time/advance），主机测试用脚本时钟推进任务；
  2. 板级事件注入收敛到 psg_sequence_io 的测试替身（与实板同接口，含 TIMA 串结束/DMA 就绪/保护事件全谱）；
  3. 增加"失约注入钩子"（编译期测试宏或注入回调）：人为延迟结算任务/丢弃某半区事件，验证 F-041 终止路径与日志（current-settlement.md:21 已有验收意图，缺实现手段）；
  4. 任务监视器经注入式 timebase/watchdog 替身驱动（呼应 F2：把 app 层对 drivers 的直用收敛为经接口注入）。
- **取舍与代价**：测试宏需保证发布版裁剪零残留（N-005 同策略）。
- **影响条款**：T-011、N-003、N-005、F-041、firmware-architecture.md:151-152/161、uart-reception.md:25、current-settlement.md:21。

### 3.4 裁定链单一所有者：ECSP 公共检查 → 状态矩阵 → 执行

- **档位：需权衡**。
- **现状证据**：pulse-engine.md:5「ECSP 任务执行公共请求检查和事务去重。调度任务将新请求经队列映射为脉冲引擎操作，并将业务结果映射为应答」；firmware-architecture.md:16-17、:24「按状态矩阵裁定请求」；SRS I-011（:122 拒绝顺序：未握手 0x04 → 长度 0x10/0x02 → 参数 0x03 → 0x14/0x15/忙）、I-007（:113 原应答回放）；params.md:58-60 PRM-101~103。
- **问题本质**：一条 0x30 的拒绝裁定跨 ECSP（握手/长度/CRC）与脉冲引擎（状态矩阵 0x14/0x15/忙）两个任务完成；事务去重要求"原应答回放"，若两级裁定分散且各自缓存，回放一致性（尤其 0x30 忙后运行结束再重传仍回放原拒绝，I-007）依赖跨任务状态拼装。
- **优化提案**：把裁定链定义为**单一定序流水线**并指定一个所有者（建议：调度任务作编排者，串行化 ECSP 公共检查 → 状态矩阵 → 执行；ECSP 只提供原语"去重查询/回放寄存/序号管理"，脉冲引擎只执行已裁定的操作）；每级输出结构化拒绝码，去重回放存"拒绝码+短载荷"而非整帧（与 2.3 联动）。
- **取舍与代价**：裁定集中在调度任务意味着它必须等脉冲引擎返回状态矩阵结论，增加一跳；收益是单一事实源、I-007 回放一致性可证。
- **影响条款**：I-007、I-011、I-012、PRM-101~103、pulse-engine.md:5、firmware-architecture.md:16-17/24。

### 3.5 编译期/运行期配置的集中登记

- **档位：明确收益**。
- **现状证据**：params.md:74 PRM-117「可配（宏）」、:213 PRM-736 编译期 `CONFIG_PSG_PROTO_UART`；firmware-architecture.md:61「拒喂阈值（板级配置）」；SRS N-005（:198 日志编译期裁剪）、F-040（:86 按 PRM-117~119 验收）；pulse-engine.md:13。

- **优化提案**：集中单一 `app_config.h`（或并入 psg_board_config.h 体系）登记全部编译期可配项（PRM-117、PRM-736、N-005 日志等级、拒喂阈值、队列容量），每项标注 PRM 引用与推导依据；params.md 的"可配（宏）"条目统一指向该头；验收固定"默认配置"为唯一基准，宏改动需回归验收清单。
- **取舍与代价**：无；纯工程化收益。
- **影响条款**：PRM-117/736、F-040、N-005、firmware-architecture.md:61。

### 3.6 设备绑定模型统一（F3 延续）

- **档位：需权衡**。
- **现状证据**：firmware-architecture.md:71「按调用场景选择静态绑定方式。发布版与调试版共享已有 UART 类型化设备模型。固定实例可直接调用构建时选定的实现，主机测试可链接同一公开接口的替代实现」；uart-reception.md:7-11 Zephyr config/data/ops 模型；embedded-layering-research.md:24「这条边界同样适合把 Flash 的擦写操作与标识记录格式分开」。

## 6. 需用户拍板的三个权衡点

1. **HRTIM 串边界机制（1.7）**：改 PRM-715（固定 0 → 按 PRM-304 派生 N-1）+ §2.4.1「更新禁用」改使能 + 台架重验，换取 1 中断/串的零抖动串结束；还是维持 REP=0 软件计数（不改已定案 PRM，但最坏 256 中断/串 + 串结束抖动）。——决定是否修改已定案的 PRM 固定值。
2. **串级结算事件流与任务边界（1.3）**：串结束事件改投结算队列 + 任务通知放行（保 PRM-117~119 预算分离，多一跳通知）；还是合并脉冲引擎与结算为单任务（零跳，但 WCET 合并、预算更难证）。——决定 1 ms 截止路径与预算体系的归属。
3. **DMA 采样归属方法学（1.8）**：固定最大缓冲 + NDTR 锚定（删除重配置协议，依赖 ISR 内 NDTR 快照可信度）；还是维持 2N 变长缓冲 + HT/TC 半区=串（保留现有语义，但跨群/勘误/中止三情形的重同步协议复杂度不降）。——决定采样归属的验证工作量与方法学。

（另：1.2 的"采样时间 12.5→6.5 周期"同样接近拍板级——它改固定 PRM-710 并关联 T-007 精度风险，但可推迟到台架给出 257 ns 窗是否落平台的结论后再定，故不占用三个拍板名额。）
