# ECSP 通用规范（通用层）

> 权威：线上协议语义与应答码。索引见 [README](../README.md)；参数见 [params.md](../params.md)。

## 1 范围与角色

### 1.1 目的与适用范围

本规范定义设备组自定义串行通信协议（Equipment Custom Serial Protocol，ECSP）的通用层：帧格式、寻址模型、通信机制、通用命令集、应答码与通用时序，作为各板卡软件设计、编码、测试与联调的共同依据，并为软件 SRS 接口需求提供实现层细节。产品/板卡级内容在预留扩展点内由对应规范定义，见附录 A。预期读者：嵌入式与主机侧软件工程师、测试工程师、协议维护与评审人员。

适用于设备组内采用 ECSP 的串行链路；USB、网络等其它接口不在范围内。

本规范只规定通用层，下列内容由实例化文档定义：

| 实例化内容 | 归属文档 |
| --- | --- |
| 产品地址分配、整机拓扑、各链路角色与板卡地址分配表 | 产品规范 |
| 板卡功能命令（PRM-025）及其载荷与业务语义 | 板卡规范 |
| 故障字各位分配（bit0 与保留位 bit1~bit7）、物理层参数与 §6 时序覆盖 | 板卡规范 |

实例化文档不得修改本规范的帧结构、通用命令语义、应答码语义与校验规则，只能在上述扩展点内补充。

### 1.2 通信架构与角色

一主多从：主机为发起方与链路管理者，从机为应答方；从机之间不直接通信。寻址唯一键为 **(产品地址, 板卡地址)**；两字段同时匹配本节点才受理，否则丢弃且无动作。

- 产品地址与板卡地址由产品规范分配；设备组内产品地址不得重复，同一产品内板卡地址不得重复；
- 同一节点可在不同链路担任不同角色，由产品规范按链路声明。

### 1.3 术语与定义

本规范用到的协议词汇以 [GLOSSARY](../../GLOSSARY.md) 的 ECSP 部分为准（会话、事务、事务序号、应答时限、长耗时命令、主动上报帧、上传模式、掉线、链路故障等）。下表只列本层反复使用、且在本规范内显式定义的词。

| 术语 | 定义 |
| --- | --- |
| UART | Universal Asynchronous Receiver/Transmitter，通用异步收发器，串行通信接口。 |
| CRC | Cyclic Redundancy Check，循环冗余校验。 |
| LSB | Least Significant Byte，最低有效字节。 |
| MSB | Most Significant Byte，最高有效字节。 |
| 主机 | 通信发起方与链路管理者。 |
| 从机 | 应答方；仅在握手、心跳与事件上报时允许主动发送，从机之间不直接通信。 |
| ECSP | Equipment Custom Serial Protocol，设备组自定义串行通信协议。 |
| 设备组 | 共享 ECSP 通用层规范的一组产品及其板卡。 |
| 节点 | 链路上的一个通信端点；同一节点可在一条链路上作主机、在另一条链路上作从机，角色由产品规范按链路声明。 |
| 产品地址 | 标识设备组内某一个产品；同一产品内的各板卡取相同值。 |
| 板卡地址 | 在同一产品总线上唯一标识一个板卡；与产品地址共同构成寻址唯一键。 |
| 产品规范 | 某一具体产品的实例化文档，见附录 A 表 10-2。 |
| 板卡规范 | 某一具体板卡的实例化文档，见附录 A 表 10-3。 |

### 1.4 文档约定

命令码、地址、应答码和帧内原始字节用十六进制，前缀为 0x。时间、波特率、次数和范围上下限用十进制并带单位。没有 0x 前缀的整数是十进制。

示例帧中的产品地址、板卡地址与应答码均直接写出具体字节（如 03、02），取值由产品规范分配（见附录 A 表 10-2）。

## 2 帧与编码

### 2.1 物理层参数

推荐取值示例如下（非强制；实际取值在产品规范中声明）：

| 参数 | 登记项 |
| --- | --- |
| 接口类型 | PRM-001 |
| 波特率 | PRM-002 |
| 数据位 | PRM-003 |
| 停止位 | PRM-004 |
| 校验位 | PRM-005 |
| 流控制 | PRM-006 |

实际取值以及其对 §6 时序默认值的影响由产品规范声明。同一链路两端应取相同参数；调整波特率时，通信双方应同步更新。

### 2.2 唯一帧结构

**表 3-1 唯一帧结构**

| 偏移 | 字段 | 长度（字节） | 说明 |
| --- | --- | --- | --- |
| 0 | 帧头 | 1 | 固定 PRM-007 |
| 1–2 | 帧长度 | 2 | PRM-009；语义 = 从帧头到帧尾的整帧字节数（含帧头、CRC、帧尾） |
| 3 | 产品地址 | 1 | 同一产品含多个板卡时，产品地址相同 |
| 4 | 命令码 | 1 | — |
| 5 | 板卡地址 | 1 | 用于在同一产品总线上唯一标识一个板卡 |
| 6…6+N−1 | 数据载荷 | N | 可为空 |
| … | 帧校验 | 2 | u16 小端（PRM-022） |
| 末 | 帧尾 | 1 | 固定 PRM-008 |

无论何种帧，产品地址与板卡地址都填被访问从机的产品地址与板卡地址；从机应答和上报不得改填主机板卡地址。

长度语义 = 整帧字节数，因此恒有 LEN = PRM-010 + payload_len（请求/事件）或 LEN = PRM-010 + 1 + data_len（应答；应答码计入载荷）。

### 2.3 帧校验

帧结构中包含一个错误校验字段，基于循环冗余校验（CRC）生成，覆盖范围为帧长度字段的第一个字节至数据载荷字段的最后一个字节；算法为 **CRC16-MODBUS**。

**CRC16-MODBUS 参数（唯一取值，不接受变体）**

| 参数 | 登记项 |
| --- | --- |
| 宽度 | PRM-015 |
| 多项式 | PRM-016 |
| 初值 | PRM-017 |
| 输入反射 | PRM-018 |
| 输出反射 | PRM-019 |
| 结果异或 | PRM-020 |
| 校验值 | PRM-021 |
| 线上字节序 | PRM-022 |
| 覆盖范围 | PRM-023 |

参考实现：Zephyr 的 `crc16_ansi()`，等价于 `crc16_reflect(0xA001, 0xFFFF, buf, len)`。

### 2.4 数据载荷编码规则

本协议中所有多字节整数、浮点数及帧级多字节字段（如帧长度、帧校验）均默认采用小端字节序（PRM-014），除非某字段另有说明。数据载荷字段编码规则如下：

- **无符号整数**：二进制原码，小端字节序。例如十进制数 513（0x0201）在数据载荷中编码为十六进制连续字节 `01 02`。
- **有符号整数**：二进制补码，小端字节序。
- **浮点数**：IEEE 754 单精度，小端字节序。
- **字符串**：默认定长字符串，ASCII 编码，帧内不含 0x00；变长字符串仅在该命令明确声明时以 0x00 结尾。

### 2.5 帧类型

帧类型决定的是怎么传、谁发起、是否需要应答。

| 帧类型 | 方向 | 绑定行为 |
| --- | --- | --- |
| 请求帧 | Host→Slave | 发出后应等待应答；绑定超时与重传 |
| 应答帧 | Slave→Host | 应带应答码；命令码应与请求相同；请求需要数据时才带数据 |
| 主动上报帧（事件） | Slave→Host | 无请求自主触发；主机不应答；单次或周期 |
| 特殊会话帧 | Host↔Slave | 仅 0x01；请求形态须应答，上报形态不应答 |

## 3 命令集合

**命令码分配**

- 0x00 保留；
- PRM-024：通用命令区为 **0x01–0x2F**，其中 **0x01–0x12 为已定义区**（通用命令见 §3.1、§3.2），**0x13–0x2F 为保留区**（供后续扩展），**0x22–0x2F 为板卡扩展段**（由板卡规范定义）；
- PRM-025：板卡功能命令区，由各板卡规范定义。

**命令类别**

命令类别决定的是做什么、是否幂等。

- 获取类：只读，语义是获取设备当前状态、传感器测量值或配置值等。该类命令具备幂等性与零副作用，多次连续获取不会改变设备的运行状态。
- 设置类：写入，语义是将一组预定义参数、阈值或配置写入设备。设计时应设计为幂等写，防止重复写入与最终预期结果不一致。
- 动作类：行为触发操作。语义是用于触发设备执行特定行为或状态机迁移。动作类命令又具体分为：
  - 幂等动作类：重复执行无累积副作用；
  - 非幂等动作类：重复执行可能导致状态错乱或物理危害，因此引入事务序号机制进行严格防护（见 §4.3）。
- 事件类：状态变更或客观事实通知。分周期上报事件类（如 0x10）与单次上报事件类（如 0x0A）。
- 特殊会话类：仅用于握手请求/握手上报（0x01）。

**表 3-3 命令类别与帧类型映射矩阵**

| 命令分类 | 承载的帧类型 | 通信流向 | 其它说明 |
| --- | --- | --- | --- |
| 获取类 | 请求帧 + 应答帧 | 主机 → 从机 | — |
| 设置类 | 请求帧 + 应答帧 | 主机 → 从机 | 应保证幂等写 |
| 动作类 | 请求帧 + 应答帧 | 主机 → 从机 | 非幂等命令应增加事务序号防护 |
| 事件类 | 主动上报帧 | 从机 → 主机 | — |
| 特殊会话类 | 特殊会话帧（及握手请求的应答帧） | 主机 ↔ 从机 | — |

**命令定义的阅读约定**

无特别声明时，应答时限采用表 7-1 中该命令类别的默认值；应答码未列出的取值含义同表 3-4。§3.2 各卡片只列该命令的载荷、差分与示例，不重复通用机制。

### 3.2 命令卡片（0x01–0x12，每条一节）

每条命令一节，字段顺序按 README §4.2。拒绝码只列该命令写明的应答码；未列出的取值按表 3-4 解释。

#### 0x01 握手请求/握手上报（特殊会话类）

| 项 | 值 |
| --- | --- |
| 命令码 | 0x01 |
| 方向 | Host↔Slave |
| 类别 | 特殊会话类 |
| 载荷长度 | 0 B（请求与上报均无载荷） |
| 幂等 | — |
| 应答时限 | PRM-101 / PRM-102 / PRM-103（同值；握手使用该默认值，见 §6.1） |
| 前置条件 | 无（「等待连接」与「已连接」阶段均处理；见 §4.2.2） |
| 拒绝码 | 0x00（完成握手）；未定义其它应答码 |

**请求载荷**

无（0 B）。

**应答载荷**

| 偏移 | 字段 | 类型 | 字节 | 约束 |
| --- | --- | --- | --- | --- |
| 0 | 应答码 | u8 | 1 | 0x00 = 完成握手，从机进入就绪并停止周期握手上报 |

**约束**

- C-0x01-01 主机下发的 0x01 为握手请求帧，须应答；从机周期上报的 0x01 为握手上报帧，主机不应答。
- C-0x01-02 从机完成初始化、自检并具备通信能力后进入「等待连接」，以 PRM-114 的频率主动发送握手上报帧，直至握手成功；连接成功后停止周期发送。
- C-0x01-03 从机在「等待连接」状态只处理握手请求帧；对其它已定义请求帧应答 0x10，对未定义或不支持实现的命令码应答 0x04，后一判定先于未握手判定。
- C-0x01-04 已就绪的从机再次收到握手请求时，判定主机意外复位：立刻停止正在执行的所有业务，应答 0x00，进入就绪；若此前因握手请求而停止周期上报，保持就绪、不再恢复「等待连接」周期上报。
- C-0x01-05 主机在该从机已连接或就绪后再次收到其握手上报帧，判定从机意外复位：停止依赖该从机的业务，会话状态置为「未连接」，回送握手请求帧并重新执行 §4.2.1（含版本核对）。

**示例**

从机主动上报帧（周期）：

```
FA | 09 00 | 03 | 01 | 02 | 88 50 | 0D
```

主机请求帧：

```
FA | 09 00 | 03 | 01 | 02 | 88 50 | 0D
```

从机应答帧：

```
FA | 0A 00 | 03 | 01 | 02 | 00 | 50 55 | 0D
```

请求帧由主机发出、上报帧由从机发出，二者由**方向**区分（Host→Slave / Slave→Host），帧内不设方向位；示例字节相同不影响识别。

#### 0x02 获取软件完整版本（获取类）

| 项 | 值 |
| --- | --- |
| 命令码 | 0x02 |
| 方向 | Host→Slave |
| 类别 | 获取类 |
| 载荷长度 | 0 B |
| 幂等 | 是（获取类零副作用） |
| 应答时限 | PRM-101 |
| 前置条件 | 已收到握手应答 0x00（「已连接」）；用于版本核对（§4.2.1） |
| 拒绝码 | 0x00（获取成功）；未定义其它应答码 |

**请求载荷**

无（0 B）。

**应答载荷**

| 偏移 | 字段 | 类型 | 字节 | 约束 |
| --- | --- | --- | --- | --- |
| 0 | 应答码 | u8 | 1 | 0x00 = 获取成功，其后为软件完整版本号 |
| 1 | 软件完整版本号 | char[7]（ASCII） | 7 | 定长，格式 X.Y.Z.N（PRM-201）；定义见《医疗器械软件注册审查指导原则（2022年修订版）》 |

**约束**

- C-0x02-01 主机收到握手应答 0x00 后应下发本命令，将应答中的软件完整版本号（PRM-201）与主机固件内宏定义的期望版本做逐字节相等比较（§7.2）。
- C-0x02-02 版本格式第 4 段为 `N`（PRM-201），与需求 I-025 一致。
- C-0x02-03 版本号载荷无结尾 0x00，比较不得按以 `'\0'` 结尾的 C 字符串处理（§7.2）。

**示例**

假设从机的软件完整版本号为 `1.0.0.0`。

主机请求帧：

```
FA | 09 00 | 03 | 02 | 02 | 88 A0 | 0D
```

从机应答帧：

```
FA | 11 00 | 03 | 02 | 02 | 00 31 2E 30 2E 30 2E 30 | FA 0E | 0D
```

## 4 通信机制

本章定义协议运行所需的动态行为规则：上电与握手流程（§4.2）、非幂等动作类命令的事务序号机制（§4.3）、长耗时命令处理（§4.4）、复位检测与恢复（§4.5）、低功耗链路行为（§4.6）。

### 4.1 通信机制概述

基础模型为请求-应答：从机应在规定应答时限内应答；超时后主机重发，含初发最多 PRM-029 次。主机对主动上报帧不应答；握手上报见 §4.2。本章另规定：握手（§4.2）、动作幂等（§4.3）、长耗时（§4.4）、复位恢复（§4.5）、低功耗（§4.6）。

### 4.2 上电与握手流程

本节定义主机与从机上电/复位后的会话建立规则，命令码均为 0x01：主机下发的为握手请求帧（须应答）；从机周期上报的为握手上报帧（主机不应答）。超时与重发规则见 §5.3。

主机对每台从机维护两条互不折叠的状态轴：**会话状态**描述会话的生命周期，**事务状态**描述在途事务的进展。重发次数只是事务上的计数器（`attempt`）与随之累加的 deadline，不是一个状态。

会话状态用词统一为：未连接、连接中、已连接、就绪、版本不符、掉线（六态，见 GLOSSARY「会话状态」）。

**表 4-1 从机会话状态**

| 会话状态 | 含义 |
| --- | --- |
| 未连接 | 尚无有效会话；可主动发握手请求，也可因收到握手上报帧而发握手请求 |
| 连接中 | 已发出握手请求，等待应答或按超时规则重发 |
| 已连接 | 已收到握手应答 0x00；尚未完成软件完整版本相等核对 |
| 就绪 | 已通过软件完整版本相等核对，允许下发业务命令 |
| 版本不符 | 握手成功但软件完整版本与主机固化期望值不相等；此时不得下发业务命令，停留在该状态直至复位或重新握手（§4.2.3） |
| 掉线 | 连续未收到该从机任何有效帧，达到掉线判据（PRM-112，见 §6.2）；从机恢复后应重新握手，不得直接恢复业务。从机低功耗时沉默不算掉线 |

**表 4-2 从机事务状态**

| 事务状态 | 含义 | 迁移 |
| --- | --- | --- |
| 空闲 | 无在途事务 | 有待发请求 → 待发送 |
| 待发送 | 已排队，尚未交给链路 | 整帧成功交给链路 → 等待应答；链路故障 → 空闲并上报 |
| 等待应答 | 已发出请求，等待应答帧，含超时重发 | 收到应答 → 空闲（长耗时命令 → 等待结果）；重发达到上限 → 掉线 → 空闲 |
| 等待结果 | 长耗时命令已受理，等待结果事件或获取结果兜底（§4.4） | 收到结果事件或获取结果应答 → 空闲 |

多从机时，各板卡地址的两条状态轴、重发计数与会话建立计时相互独立。

#### 4.2.1 主机上电操作

主机自身上电或复位后，不得假设从机状态确定，应按下列顺序重建会话。

**（1）主动握手探测**

若从机在主机复位前已完成握手并处于就绪，从机不会再周期发送握手上报帧，主机仅靠等待上报无法重建会话，因此主机应主动下发握手请求帧（0x01）。握手请求按超时重发规则做应答超时重发，同一轮探测含初发最多发送 PRM-029 次。发出请求后主机将该从机会话状态置为「连接中」。

**（2）主动探测失败后的被动等待**

若含初发共 PRM-029 次仍未收到握手应答：

- 将该从机保持或迁回「未连接」；
- 进入被动等待：等待该从机主动上报的握手上报帧（0x01）；
- 被动等待期间，一旦收到该从机握手上报帧，主机应立即再次进入步骤（1）下发握手请求帧进行接纳；
- 被动等待不得超过会话建立总时限 PRM-108（取值与覆盖规则见 §6.3 默认值与覆盖）。超时仍未握手成功时，主机按掉线判据（§6.2.1）处理并告警。

被动等待覆盖从机仍处于「等待连接」的情形；若从机已就绪但不回包，则仍依赖步骤（1）及会话总时限内的再次探测。

**（3）版本核对与安全配置**

主机收到从机对握手请求的应答 0x00 后，判定握手成功，将该从机会话状态置为「已连接」。此后主机应：

- 下发获取软件完整版本（0x02）命令，将应答中的软件完整版本号（PRM-201 的定长字符串）与主机固件内宏定义的期望版本做逐字节相等比较（见 §7.2）；
- 完全相等后，方可将该从机置为「就绪」并下发业务命令；不相等时，主机应将该从机置为「版本不符」，不得进入「就绪」并报警。

在整个上电/复位重建过程中，主机均可接收从机主动发送的握手上报帧（0x01），对握手上报帧不应答，仅在「未连接」或判定需重建时，用握手请求帧完成接纳。

#### 4.2.2 从机上电操作

从机上电完成初始化、自检并具备通信能力后，进入「等待连接」状态，以 PRM-114 的频率主动发送握手上报帧（0x01），直至握手成功。

在「等待连接」状态下：

- 从机仅处理主机下发的握手请求帧（0x01）；
- 对其它已定义的请求帧一律应答 0x10（未握手拒绝），不执行对应业务；
- 未定义命令码或不支持实现的命令码一律应答 0x04，该判定先于未握手判定。

连接成功后进入「已连接」状态，并停止周期发送握手上报。

#### 4.2.3 握手异常场景处理

下列规则仅适用于双方已经完成握手之后（从机处于「已连接」，主机侧该从机至少为「已连接」或「就绪」）。上电置态完成前的早到帧、以及「未连接/连接中」阶段收到的握手上报帧，不适用本小节的意外复位判定。

- 主机意外复位（从机侧判定）：若从机在已就绪后再次收到主机下发的握手请求帧（0x01），则判定主机为意外复位：立刻停止正在执行的所有业务，应答 0x00，进入「就绪」状态（若此前因握手请求而停止周期上报，保持就绪、不再恢复「等待连接」周期上报）。主机侧按 §4.2.1 继续完成版本核对与安全参数重配。
- 从机意外复位（主机侧判定）：若主机在该从机已连接或就绪后，再次收到其上报的握手上报帧（0x01），则判定从机为意外复位：立刻停止依赖该从机的业务，将该从机会话状态置为「未连接」，并回送握手请求帧，重新执行 §4.2.1（含版本核对）。意外复位与预期复位的后续恢复差异见 §4.5。

### 4.3 动作类命令的幂等控制

动作类命令用于触发物理过程或驱动状态机跃迁。其中：

- 非幂等动作（如能量触发、状态翻转等）重复执行会导致物理危害或逻辑错乱；
- 天然幂等动作（如停机、故障清除、绝对位置归零等）重复执行无物理累加危害。

由于串行链路存在「从机已执行但应答丢失」的可能，主机超时重传极易引发非预期二次执行。为保证可靠性，非幂等动作类命令应在帧载荷首字节携带 1 字节事务序号（PRM-027），由从机实现去重与重传结果回放。具体规则如下：

- **字段定义与编号空间**：非幂等动作类命令的请求帧载荷首字节为 1 字节事务序号。主机为每台从机维护独立的单调递增计数器，取值范围为 0~255，溢出后自动回绕（PRM-027）。
- **事务绑定与重传复用**：主机在每次新发起非幂等动作命令时应分配新的事务序号；当发生通信超时、校验失败触发的同一次事务重传时，应复用初始事务序号，严禁重传递增事务序号。
- **结果缓存与去重回放**：从机维护一张先进先出（FIFO）的事务序号缓存，以 (命令码, 事务序号) 为唯一索引，缓存最近执行完毕的应答帧（含应答码及关联状态）：
  - 从机收到非幂等动作请求时，优先检索缓存表；
  - 若命中缓存，从机严禁重复调用底层硬件驱动，直接将缓存的应答帧重新回传给主机；
  - 若未命中缓存，从机按新事务进入底层执行流程；
  - 缓存生命周期：从机发生软复位后，以及每次收到握手请求帧（0x01）时，清空该缓存。后者保证主机重启后其重新从 0 开始的事务序号不会命中上一次运行留下的旧条目。
- **豁免范围**：获取类命令、设置类命令以及幂等性动作类命令不携带事务序号字段，协议层不进行去重拦截。幂等性动作类命令仍应按请求-应答返回确定的执行状态。

### 4.4 长耗时命令处理机制

长耗时命令采用「先应答、后执行、事件通知结果」机制：

- **从机先应答后执行**：第一次应答 0x00 并携带最长执行时间（T_exec_max）。该字段为 2 字节无符号整数（u16），单位为毫秒（ms），小端字节序。表示已受理并开始执行，从机进入 BUSY，主机据此启动定时器；若拒绝则回相应应答码且不携带该字段、无后续结果事件。
- **从机结果事件通知**：从机执行结束（含成功、失败、中止）后以独立事件命令单次上报结果，结果事件无应答、无重传。
- **「获取执行结果」命令兜底**：每个长耗时命令应配有相应的「获取执行结果」命令，用于主机在等待结果时发生超时或结果事件丢失时的兜底。「获取执行结果」命令的应答帧中，应答码表示本次获取是否成功，结果码表示长耗时命令的执行状态。
- **从机执行超时**：主机应先发送获取结果命令。若应答码为 0x00 且结果码为 0x00，表示从机实际已完成、仅结果事件丢包，可正常闭环；若应答码为 0x00 且结果码为 0x11（操作正忙），表示从机仍在执行但已超过最长执行时间（T_exec_max），主机应下发对应停止控制（控制码 0x01）主动终止。停止应使用新的事务序号。
- **长耗时命令执行期间的保活**：从机对于主机下发的获取类命令可正常接收，从机的心跳命令保持上传。

#### 4.4.1 长耗时动作执行期间到达的其他动作类/设置类命令

在从机进行长耗时动作执行期间，若有其它动作类/设置类命令到达，分为三类不同的处理策略：

- 安全抢占类：意图就是终止当前动作，从机应响应。包括该动作对应的停止命令，以及系统复位（0x07）。
- 正交类：与当前动作无共享硬件或业务依赖时，应并发执行。
- 互斥类：竞争同一执行器或业务互斥时，应拒绝且不动作，应答忙（0x11）。

### 4.5 复位检测与恢复

从机复位来源包括：主机下发的系统复位（0x07）命令、硬件复位（看门狗、掉电重启、欠压复位）与软件异常复位。主机应能够判定复位性质并按流程恢复会话，判定规则见表 4-3。

**表 4-3 复位性质判定**

| 场景 | 判定 | 处理 |
| --- | --- | --- |
| 主机下发系统复位（0x07）命令并收到应答后，一段时间过后收到该从机的握手（0x01）命令 | 预期复位 | 按 §4.2.3 重新握手 |
| 从机已经完成握手、主机未下发系统复位（0x07）命令，却收到该从机握手请求/握手上报（0x01）命令 | 从机意外复位 | 停止依赖业务，按恢复流程重建会话，并评估误复位根因 |
| 「等待连接」状态下掉线门限内无任何帧 | 疑似掉电或链路中断 | 按掉线判据（§6.2.1）处理 |
| 复位后获取软件完整版本（0x02）命令返回的软件完整版本与主机固化期望版本不相等 | 固件被更换或升级生效 | 按 §7.2 相等核对；不相等则置为「版本不符」并报警 |

意外复位与预期复位的恢复流程相同：

- 主机收到握手请求/握手上报（0x01）命令后，将该从机会话状态迁回「连接中」；若 BUSY，取消在途事务并记录执行中断；
- 回送握手命令完成接纳（见 §4.2.3）；
- 下发获取软件完整版本（0x02）命令，按 §7.2 与主机固化期望版本做相等核对，必要时抽查获取硬件版本（0x04）命令/获取序列号（0x06）命令确认配置未变；
- 重新配置安全相关参数后恢复业务；预期复位可跳过根因评估，意外复位应在恢复后完成根因记录。

长耗时命令执行期间（BUSY）收到系统复位（0x07）命令，按抢占式复位处理：

1. 从机立即按板卡规范为该命令定义的安全中止序列停止在途动作，使执行器进入安全态；
2. 中止完成后应答 0x00，随即执行复位；
3. 不发送该长耗时命令的结果事件（复位会丢弃它），事务不进入「等待结果」；主机重新握手后应重新查询状态，不得假设在途命令的结局；
4. 若在途命令无法安全中止——板卡规范未定义其安全中止序列，或中止序列自身执行失败——从机应答应为 0x20 且**不执行复位**，同时置故障位并上报（0x11）；
5. 中止与复位序列执行期间到达的第二条 0x07 应答 0x11。

复位是主机最后的恢复手段，不能被从机的忙状态否决；但「抢占」不等于「硬断电」：安全中止序列由板卡规范为每条长耗时命令定义（附录 A 表 10-3 第 14 项），未定义该序列的命令不得实现为长耗时命令。

### 4.6 低功耗链路行为

设置低功耗模式（0x0B）的链路行为如下。命令字段、应答差分与示例见 0x0B 卡片。芯片如何进入低功耗硬件态由产品或板卡规范定义；本规范只规定链路行为。

进入低功耗的应答 0x00 入队之后，从机停止一切主动上报：不再发送心跳（0x10）；已排队的故障上报（0x11）与结果事件（0x0A / 0x0E）也先不发，退出低功耗后再允许发出。会话保持就绪。从机仍应答收到的请求帧。

主机在收到进入低功耗的 0x00 之后，暂停对该从机的掉线判定（见 §6.2.1）；会话仍为就绪。进入低功耗的应答丢失时，主机按表 7-1 设置类 PRM-102 重发同一帧，含初发共 PRM-029 次；该次数用尽仍无 0x00 则不暂停掉线判定。已确认低功耗后再发进入，从机应答 0x00 并继续保持安静。

确认低功耗之后，主机只允许再下发进入低功耗、退出低功耗与系统复位（0x07）；其它业务命令在本地拒绝，链路上不出现对应帧，且该拒绝原因与「会话不是就绪」相区分。退出低功耗的 0x00、握手请求被受理并离开低功耗、或会话因复位/重新握手重建之后，心跳与掉线判定恢复。

低功耗期间收到握手请求时，从机离开低功耗并按 §4.2 / 0x01 既有握手规则继续。低功耗期间若到达握手、进入、退出、复位以外的帧，从机照常应答并保持低功耗。长耗时命令执行中进入低功耗应答 0x11。

**主机处理要求**

- 0x00：事务完成；长耗时命令登记在途（含最长执行时间（T_exec_max））。
- 0x01 / 0x02 / 0x03 / 0x04：记录日志，报告缺陷，不重试。
- 0x10：先完成握手（见 §4.2）再重发。
- 0x11：等待结果事件，或最长执行时间（T_exec_max）超时后获取兜底；若该 0x11 是对复位请求的应答，等从机复位后按 §4.2 重新握手。

- 0x13：检查并满足前置条件后重试。
- 0x14：先解锁（产品命令）再重试。
- 0x15：停止自动重试，上报用户并走安全流程。
- 0x20：按产品安全策略处理；设备级故障经故障上报（0x11）命令/获取故障状态（0x12）命令上报。

### 6.2 心跳监控

#### 6.2.1 主机

主机为每个从机维护最后活跃时间。收到该从机任一主动上报或应答即更新。以 PRM-113 为周期检查：当前时间减最后活跃时间大于掉线判据（PRM-112），则将会话置为掉线。

非易失写入（0x03、0x05）含初发共 PRM-029 次、每次最长按 PRM-104 / PRM-105 的应答等待，不按本条提前判掉线。重发次数用尽仍无应答后，事务超时，会话进入掉线。已确认低功耗期间的沉默不判掉线，见 §4.6。

#### 6.2.2 从机

从机以 PRM-113 为周期检查：若距上次成功发出主动上报或应答已满该周期，则发送心跳（0x10）。低功耗期间不发送，见 §4.6。

| 长耗时命令最长执行时间（T_exec_max） | 由板卡规范按命令声明；u16，单位 ms，上限 PRM-109 | 可 | 预计超过上限的命令应改用「结果事件 + 获取结果」机制，不得依赖单个 T_exec_max |

## 7 版本与兼容

### 7.1 协议版本规则

协议版本号采用 V X.Y 格式：X 为不兼容变更（帧结构调整、既有命令码含义变更等），Y 为兼容性新增（新增命令、新增字段等）。协议版本不设独立的帧字段，随固件版本管理：通过获取软件完整版本（0x02）命令并按 §7.2 核对确认；双方版本不一致时的处理方式见 §4.2.1 与 §7.2。

命令码一经发布不得复用或变更含义；废弃命令应保留定义，并在对应板卡规范中标记为废弃。

### 7.2 版本核对与实例声明

主机在固件中固化本产品期望的从机软件完整版本号，该版本号为定长 ASCII 字符串，格式为 `X.Y.Z.N`（PRM-201），与获取软件完整版本（0x02）命令应答载荷中的软件完整版本号编码一致。

握手成功后，主机应：

1. 下发获取软件完整版本（0x02）命令；
2. 将应答中的软件完整版本号与主机固化的期望版本做逐字节相等比较（实现上可采用对定长版本号的 `memcmp` 等；载荷无结尾 `0x00`，不得按以 `'\0'` 结尾的 C 字符串对未终结缓冲调用 `strcmp`）；
3. 仅当完全相等时允许将该从机置为「就绪」；不相等时应将该从机置为「版本不符」，不得下发业务命令并报警。

协议版本与固件版本的对应关系由产品规范声明，模板见表 9-1。

**表 9-1 协议版本与固件版本对应（由产品规范填写）**

| 协议版本 | 适用产品/板卡 | 期望软件完整版本 | 备注 |
| --- | --- | --- | --- |
| V1.0 | 【产品名 / 板卡名】 | 【X.Y.Z.N】 | 【备注】 |

### 7.3 变更管理

本规范的任何变更应执行变更控制流程：评估对设备组内各产品与板卡软件的影响、相关方联合评审、更新协议版本号与修订记录、通知所有相关方、执行回归测试。未经评审的临时改动不得引入代码。

板卡功能命令与产品级内容的变更由对应板卡规范或产品规范按各自变更控制流程管理，但不得违反本规范的通用规则；确需修改通用规则的，应先变更本规范。

## 8 安全要求

对安全关键命令应定义保护措施。通用层认定的安全关键命令见表 8-1；板卡功能命令中的安全关键命令（如治疗输出控制、参数下发、标定、存储清除等）由板卡规范认定，并给出与表 8-1 同等的保护措施。

**表 8-1 通用安全关键命令保护措施**

| 命令 | 风险说明 | 保护措施 |
| --- | --- | --- |
| 系统复位（0x07） | 误复位导致在途业务中断 | 应先应答再复位；使用事务序号防止重发导致重复复位；长耗时命令执行期间为抢占式复位：先按板卡规范的安全中止序列进入安全态，再应答 0x00 并复位；无法安全中止时应答 0x20 且不复位（见 §4.5） |
| 在线升级（0x0C） | 升级失败导致功能不可用 | 升级包签名验证、分包应答确认、失败回滚至上一有效版本；停止应使用新事务序号；擦写失聪窗口内主机不得雪崩重传 |
| 设置硬件版本（0x03）/ 设置序列号（0x05） | 错误写入导致唯一标识与追溯失效 | 限制为生产/维护模式；载荷格式校验失败不得改写；写入后应做持久化校验 |

协议层通用要求：

- 所有命令应执行参数合法性校验（类型、取值范围、状态互斥关系）；
- 非幂等安全关键命令应按 §4.3 使用事务序号；
- 安全关键命令的保护措施应与产品风险管理报告及 SRS 安全需求建立映射，映射由产品规范给出。

## 9 符合性要求

### 9.1 符合性措辞与声明

本规范用下列三级措辞描述要求（按 README §3）：

- **应（强制级）**：强制要求。不满足即不构成 ECSP 符合实现；
- **应（默认级）**：默认要求。偏离应记录理由并经评审；
- **可**：由板卡规范选择是否实现。

符合性声明方式：

- 每份板卡规范应填写符合性矩阵，声明其对本规范每条通用命令的支持级别与覆盖值；本仓库由板卡规范自建符合性矩阵（见 board-pulse-gen.md §6）。
- 支持级别为「可」而该实现未实现时，从机收到该命令应应答 0x04（不支持的命令操作），不得复位或死机；
- 主机应按板卡规范声明的符合性矩阵固化每个节点的命令表，不得向节点下发其声明为不支持的命令。

### 9.2 板卡功能命令的实例化要求

PRM-025 为板卡功能命令区，语义由板卡规范定义。通用层对板卡功能命令提出下列应满足的要求：

- **命令码**：不得与通用命令码冲突；同一板卡规范内不得重复；一经发布不得复用或变更含义，废弃命令应保留定义并标记为废弃；
- **复用通用机制**：请求-应答与超时重传（§4.1）、应答码（§5.1）、非幂等动作的事务序号（§4.3）、长耗时命令的 T_exec_max 与结果事件及获取结果兜底（§4.4）、主动上报帧约束，均按本规范执行，不得另立机制；
- **应答时限**：板卡规范未为该命令写明毫秒数时，用表 7-1 的默认值（PRM-101 / PRM-102 / PRM-103 同值）。写明的毫秒数只属于该命令。命令类别不决定主机等多久；
- **不得修改通用层**：帧结构、地址模型、通用命令语义、应答码语义、校验与编码规则；
- **不支持的命令码应应答 0x04**，不得复位或死机；
- **内容完整**：板卡规范应给出附录 A 表 10-3 列出的内容，并填写符合性矩阵（本仓库见 board-pulse-gen.md §6）。

状态类拒绝的应答码映射见表 5-4。
